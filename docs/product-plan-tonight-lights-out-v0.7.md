# 今晚关灯 · 产品方案 v0.7

2026-11-07 · 产品评审与首版实施建议

**结论：值得做，但不建议照 v0.6 全文开发。** 夜景和关灯动作具备辨识度；「很多人一起」能增加陪伴感，但还不足以成为产品赖以成立的前提。v0.7 的主张是：**给舍不得结束今天的人，一个轻轻关灯的动作。一个人用也成立，有人一起时更温暖。**

本稿替代 [v0.6](product-plan-tonight-lights-out-v0.6.md) 作为下一轮产品验证的建议方案，可独立阅读。它是产品决策稿，不表示功能已经实现或已经获得用户验证。本次核对了仓库实现与部分平台一手资料；尚无真实用户访谈、留存数据、渠道转化、真机性能或运营成本证据。以下按小团队、尚未证明产品需求的阶段安排优先级；已有用户规模和预算仍需在执行前填入。

---

## 一、v0.6 哪些值得保留，哪些必须调整

### 值得保留

1. **用关灯代替普通打卡。** 从冷白到暖黄再到熄灭，动作、情绪和品牌可以连在一起。
2. **完成之后帮助用户结束使用。** 不追加任务，不用排行榜或断签惩罚制造负担。
3. **白天有内容可看。** 分享与回看可以在用户方便时发生，不挤在睡前。
4. **先缩减好友关系功能。** 首版不承担申请、授权、状态监督和关系维护。
5. **本地晚安句和真实记录是底座。** 没有公共内容、没有其他在线用户，自己的那次关灯仍然完整。

### 需要调整的八件事

| v0.6 的判断或设计 | 问题 | v0.7 的决定 |
| --- | --- | --- |
| 把「共时」升为唯一内核 | 冷启动少于 100 人时又隐藏人数，最需要验证时反而看不到主卖点 | 个人收尾是核心；集体数据是增强。少量真实参与也可呈现 |
| 换楼、月相、每天不同能带来回访 | 新鲜感不等于持续需求，第三次打开仍可能无事可做 | 先验证是否会在下一晚主动想起这个动作，再投入变化内容 |
| 晨报承担第二次打开 | 集体曲线与昨天看过的一句话，不一定值得早上专程打开 | 改为「昨夜回执」；下一晚再用是主循环，白天回看是可选循环 |
| 冷白窗表示还醒着，暗窗比例取已关灯 / 活跃人数 | 没有真实清醒状态；活跃人数增加还会导致暗窗重新变亮 | 背景是插画；只让自己的窗表示个人记录，不给陌生人编造状态 |
| 分片计数提供「你是第 N 个」 | 近似总量不能产生稳定、唯一的精确序号，写在代码注释里也无法消除误导 | 删除序号和名次，只保留真实聚合与自己的记录时间 |
| 完成后 60 秒取增量，再播放连锁熄灯 | 视觉高潮要求用户留下等待，宣传片却在几秒内展示它 | 完成反馈在自己的动作中结束，删除等待他人熄灯机制 |
| P0 做复杂画面，个人晨报和分享放 P1 | 花费较大后仍验证不到个人价值、分享和新用户承接 | P0 做完整的小闭环；月相、公共曲线和 UGC 后移 |
| 分享图生成率、次日打开率代表传播与晨报价值 | 生成不等于分享，打开也不等于看过晨报；低留存未必是文案问题 | 分开测量使用、回看、分享发起、接收访问和新用户真实关灯 |

原稿还有几处直接矛盾需要撤销：首屏示意仍出现「此刻还有 N 扇亮着」；本产品记录被称为「全国人睡觉的曲线」；全局 04:00 切夜与目标 03:00、窗口结束 09:00 冲突；「最近结束的一夜」与「最近有记录的一夜」混用；`readCount` 被直接解释为读过的人数。这些不是文字润色问题，会改变实际产品行为。

**对“爆款”的判断：有做出记忆点的机会，尚无支持规模传播的证据。** 首先证明陌生人看得懂、自己会再用、愿意把它带给另一个人。短期曝光很高、日常反复使用、自传播增长是三种结果，不能互相替代。停留时长和 UGC 也不是爆款的必要条件，不应为了它们牺牲产品用途。

## 二、到底服务谁，提供什么价值

### 首轮用户

优先招募这样的人：夜间已经觉得该休息，却习惯继续刷微信或内容应用；不想再装一套复杂自律工具，也不喜欢被公开监督。年龄可暂以 20–35 岁招募，但行为比年龄重要。

他们需要的不是再听一次早睡道理，而是尝试一个很低成本的结束动作：

> 我已经决定今晚先到这里，希望用几秒钟把这个决定落下来。

这是待验证的需求假设。不要把所有晚睡者都当作目标用户，也不优先为轮班、需要白天睡觉、想要强制锁机或专业睡眠服务的人扩展首版。

### 对用户的承诺

**「按住关灯，今天先到这里。」**

小程序记录的是用户主动完成的关灯仪式。它不知道用户何时真正睡着，也不能确认退出之后是否继续刷手机。因此产品不说「你睡了七晚」「改善了睡眠」「大家都睡着了」，不把关灯时间包装成入睡时间。实验可以询问用户是否感觉更容易收尾，但必须标明是自述。

### 与已有产品的差异

| 参考 | 官方展示的机制 | 对本项目的启发 |
| --- | --- | --- |
| [SleepTown](https://sleeptown.seekrtech.com/) | 将规律就寝、起床与建造城镇相连 | 「睡觉 + 城市」并不独特，不能只靠楼窗画面声称品类创新 |
| [Pokémon Sleep](https://www.pokemonsleep.net/en/pokemon/) | 夜间记录、早晨研究睡姿、白天养成 | 它的早晨有新增收集内容；本项目仅靠一张曲线，不能推断同样有回访动力 |
| [Forest](https://www.forestapp.cc/) | 专注过程变成逐渐积累的森林 | 可见的个人积累比每天随机换背景更值得验证；这里不照搬惩罚或锁机机制 |

以上是机制对照，不是市场规模或增长效果证明。今晚关灯更适合尝试的区别是：**微信里随手可用、几秒钟完成、没有失败惩罚、留下属于自己的夜晚。** 画风能吸引第一眼，但是否真正帮助用户收尾、是否形成可记住的使用场景，才决定下一次打开。

## 三、三个循环，各自成立

### 1. 核心使用循环：今晚收尾，下一晚再来

准备结束刷屏 → 打开自己的窗 → 关灯 → 一句晚安 → 离开。

下一晚，当同样的「还想再看一会儿」出现时，用户想起这个动作。这是首先要验证的留存。没有晨报、分享和其他用户，也应完成这一圈。

### 2. 个人回看循环：我的夜晚被留下了

一次真实关灯 → 留下一张固定的夜晚回执 → 白天或以后回看 → 最近七晚逐渐留下记录。

不要求早上再完成任务，不设置早起领奖、补签、断签清零。七晚记录只说明哪些夜晚使用过；空白不涂红、不扣分，晚一点也用同样的星点。

### 3. 传播循环：表达自己，接住别人

一张能表达「今天先到这里」的图 → 用户自愿保存或转发 → 接收者看懂关灯动作 → 白天可演示、夜间可真实使用 → 成为新的使用者。

这里需要同时回答两句话：

- 发送者为什么分享：这句话或这张夜景表达了我的状态，愿意留存或让朋友看到。
- 接收者为什么打开：这个动作是什么、我也能不能试一下。

「全国有多少人」对接收者未必有吸引力；先让卡片像用户自己的表达。分享不解锁奖励，不要求邀请好友，不展示别人是否睡觉。

## 四、首版完整体验

两个 Tab：**今晚 / 我的**。今晚承载仪式和白天回执，我的承载目标时间、最近七晚、隐私和反馈。不存在必须连续完成的双日活任务。

### 4.1 第一次进入

**夜间且窗口已开：** 直接看见夜景和自己的窗，出现一次简短说明「按住关灯，今天先到这里」。默认目标 22:30，在首次说明或设置入口明确可改；不先要求昵称、头像或好友授权。

**白天或窗口未开：** 一张夜景预览，主动作「看一次关灯」，旁边说明「演示，不计入记录」。演示约 3 秒，完整展示自己的窗变暖、熄灭和一句晚安，不伪造其他人联动。结束后显示实际开窗时间和设置入口；用户也能直接跳过演示。

白天新用户不必等到晚上才知道产品是什么。演示与真实记录在标题、按钮和数据上分开，演示不写打卡、不进入人数、不生成“我已关灯”的个人回执。可提供一次「添加到我的小程序」的操作说明，是否有效要观察；不把它当作后台提醒能力。

### 4.2 真正关灯

默认长按 800ms；按下时自己的窗开始变暖，随后光线收拢。按满后提交一次，服务端确认后用约 1 秒熄灭。等待期间显示「正在确认」，不提前展示成功。

轻点替代入口始终可发现，触达区域与主控件同样可用；两种方式进入同一提交流程。松手过早、滑出、页面隐藏取消未完成按压。按压时跨过窗口结束则重新校验，不把过期操作写进下一夜。

网络超时显示「暂时没确认，点此查看结果」，先查询已有记录再决定重试。不能因为客户端没收到结果就断言失败，也不能靠按钮防重代替服务端幂等。没有网络时仍可看演示和已缓存回执，但不计一次新的真实关灯。

### 4.3 完成：这时就已经结束

```text
                灯灭了。

          今天就到这里。
          剩下的，明天再说。

              [ 放下手机 ]

           这一晚，已经留下了。
```

「放下手机」由用户点击触发退出；失败时保留完成态，提示可使用微信自带入口离开。按钮退出不是锁屏，更不代表已经入睡。

完成页不弹分享、不倒数、不要求等其他窗熄灭。最后一行是说明，不伪装成现在必须点击的奖励入口。本次成功始终停留完成态直到用户离开，即使此时已过 06:00。再次进入时，06:00 前恢复完成态，06:00 后按白天规则展示回执；两种情况都不再刷一次仪式或换一句话。

保留系统菜单的自愿分享能力，分享默认指向通用体验介绍，不自动公开自己的时间。睡前不主动索取分享，与禁止用户自发推荐是两件事。

### 4.4 白天：昨夜回执

用户昨夜完成过，优先展示自己的内容：

```text
                 昨夜

            [ 昨夜的夜景 ]

          你在 23:18 留下了一次关灯。
          今天就到这里。剩下的，明天再说。

          [ 留下这张图 ]   [ 发给朋友 ]

          最近七晚  ·  ·  ☆  ·  ☆  ☆  ·
```

回执保存当时的画面版本、实际显示的句子和服务端确认时间。第二天不能重新抽签，再说这是用户昨晚读到的内容。P0 只使用本地编辑句，稳定优先于内容数量；展示定稿后不被迟到的网络结果替换。

最近七晚采用固定日历位置，点亮的是使用记录，不叫睡眠成绩。P0 先做可点开的日期、时间和原句，不新增复杂统计图；既有连续、累计数据保留兼容读取，不以连续数字刺激首页回访。日期变化时窗口自然向前移动，没有清零惩罚。

| 状态 | 页面处理 |
| --- | --- |
| 昨夜有记录 | 昨夜回执及可保存的图片 |
| 昨夜没有记录 | 「昨夜还没有关灯记录」，可看演示、最近七晚与今晚开窗时间；不说用户没有睡觉 |
| 很久没来 | 首先给当前日期的入口；下方以具体日期展示「上次留下的夜晚」，不把旧记录称作昨夜 |
| 已完成但仍在凌晨 | 06:00 前优先完成态，避免刚关灯立刻变成晨间分享页 |
| 06:00 后，自己的窗口仍开放且未完成 | 仍可完成自己的这一晚；不能仅按钟表时间把 03:00 目标用户切走 |
| 窗口已关闭但还没到 06:00 | 安静的已结束状态和下次开窗时间，不称晨报、不引导长时间阅读 |

时间均按首版支持的北京时间。分享落地页不受首页昼夜状态影响，随时可看公开卡片；详细周期规则见第八节。

## 五、视觉：记住一扇窗，置身一片夜景

沿用 v0.6 的深紫夜空、近黑楼体与暖白文字。主画面仍是一片夜景，自己的窗是稳定、清晰的视觉中心。第一次可有一个轻标签帮助识别，不能只依赖颜色或呼吸光。

| 元素 | 语义 |
| --- | --- |
| 自己的冷白窗 | 这一晚尚无关灯记录，不代表用户一直清醒 |
| 自己的暖黄窗 | 正在进行仪式 |
| 自己的暗窗与星点 | 服务端已确认这一晚的记录 |
| 其他楼窗 | 美术背景，没有陌生人的在线、清醒或入睡含义 |
| 后续公共人数 | 独立文字呈现，明确指本产品的关灯记录 |

**首版一套打磨好的夜景即可。** 不每天随机搬动自己的窗；最多用少量预制天空变化增加层次，同一晚稳定。日期种子、真实月相、节气、流星雨后移，且如果以后引入天文元素，需要分别验证数据来源、时区、资源体积和低端机效果，不能称为零成本。

保留宋体气质，但保证系统无衬线降级仍然成立。晚安句建议 1–2 行短句，长文不能靠不断缩字号塞入首屏。按钮触达高度至少 44px；覆盖 320px 宽屏幕、放大字号、深底文字对比度和 Android 字体差异。

技术上先比较「静态背景 + 自己的窗的小范围动效」与必要的 Canvas 实现，用真机结果选择，不把固定 240 扇窗、分层 Canvas、某种帧率阈值预先写成产品要求。只动需要回应用户的部分，不为了检测设备性能额外运行一段重动画。

提供小程序内的「减少动效」选项；能可靠读取系统偏好时再同步，不能未经验证假定各微信端都有一致接口。关闭呼吸、缩放等装饰动作后，操作与成功状态仍应清楚。默认静音，轻震动可关闭。

## 六、分享：P0 就把入口和出口接通

### 6.1 三种载体，同一份内容

| 载体 | 用途 | 内容与规格 |
| --- | --- | --- |
| 个人回执图 | 收藏、朋友圈图片或其他内容平台手动发布 | 建议 3:4；夜景、一句晚安、日期、小品牌标识与小程序码 |
| 聊天卡片 | 微信好友或群聊中自愿推荐 | 按 5:4 构图；短标题、关灯视觉、公开落地路径 |
| 朋友圈转发 | 系统菜单分享 | 单独适配 1:1 封面和 query；待单页落地能力验收后开放 |

P0 不把精确关灯时间、昵称或账号信息印在公开卡片上；自己的回执里仍能看到时间。在线落地页只放夜景、预设晚安句、日期和体验入口。若用户确实想分享时间，后续再增加可选项与最终效果预览，首版先用一种清楚的默认输出。

卡片不是数据海报。首轮可比较两种表达：「今天先到这里」偏个人状态；「给今晚一个句号」偏动作邀请。不是预设某一种天然适合小红书，要观察用户是否真的愿意拿它表达自己。

### 6.2 接收者必须能走下去

公开卡片 → 简短动作说明 → 「试试关灯」 → 根据时间进入演示或真实仪式。

接收者不必先填资料，也不能看到发送者的私密历史。链接使用不透明来源标识和允许公开的内容版本，不暴露 UID；不存在自动加好友、自动投稿或替别人打卡。P0 复用公开的编辑内容，不建立逐张卡片的管理或撤回系统；内容版本失效时仍可进入产品介绍，不做空白错误页。

朋友圈落地需要单独验证单页模式下的能力，公开展示不依赖个人档案或受限调用；先能读，再引导进入完整小程序体验。聊天、朋友圈、图片内小程序码不可假设是同一条运行路径。平台差异依据 [微信官方 Page 类型](https://raw.githubusercontent.com/wechat-miniprogram/api-typings/master/types/wx/lib.wx.page.d.ts) 和 [CloudBase 分享说明](https://docs.cloudbase.net/recipes/add-share-with-params-miniprogram)。

### 6.3 保存与转发不是同一个结果

图片生成成功、相册保存成功、分享面板被发起、接收者访问、新用户完成关灯，分别记录。微信分享事件用于提供分享内容，不能用它证明用户最终点了发送；应从接收方的带参访问判断实际触达。依据同上。

保存权限被拒绝时保留预览，可由用户主动打开设置；不反复弹授权，也不承诺长按预览一定能绕过权限限制。相册和预览能力参照 [微信官方 API 类型](https://raw.githubusercontent.com/wechat-miniprogram/api-typings/master/types/wx/lib.wx.api.d.ts)，具体端侧行为仍待真机验收。

小程序码按卡片用途缓存复用，遵守实际接口频率限制；删除 v0.6 中未经核实的「getUnlimitedQRCode 有日调用上限」。[CloudBase 官方说明](https://docs.cloudbase.net/recipes/add-share-with-params-miniprogram) 将 getUnlimited 与有总量限制的其他码接口区分，不能混为一谈。

## 七、陪伴和 UGC：有价值再增加

### 7.1 集体数据成为增强层

基础版不以人数存在为前提。有能力可靠聚合后，在不增加夜间操作的地方显示：

> 今晚已有 12 位用户在这里留下关灯记录。更新于 23:10。

数字少也不伪装热闹，不用 100 / 2,000 人的三段阈值来切换产品。为零可写「今晚，先从你这一盏开始」；公共快照不可用时直接隐藏这行，自己的记录照常成立。

计数表示按用户与本产品的夜晚去重后的参与记录，不是当前在线人数、真实清醒人数、已睡人数或全国样本。自己的记录已成功而公共快照尚未更新时，显示「已记下，公共统计稍后更新」，不要本地随意加一制造另一个口径。

不做精确排名，不以新增活跃人数作亮暗比例，不播“其他人跟着你睡”的动画。集体时间分布只在规模和回看需求足够时再做；少量样本不展示细时间桶，也不开放可交叉筛选的地域、群组切片。统计图必须称为「本产品关灯记录的时间分布」，没有真实峰值就没有峰值故事。

### 7.2 晚安句先由编辑供给

P0 用稳定的预设句。可以先整理 12–24 句，不需开放投稿来填库存；每晚保存 `contentVersion + phraseId` 和已展示结果，内容升级也不篡改旧回执。

示例语气：

- 今天就到这里。剩下的，明天再说。
- 没做完的事，今晚先放一放。
- 这一页先合上。晚安。
- 明天的事，留给明天的你。

这些是编辑文案，不伪装成陌生人投稿。不写睡眠疗效，不把放松变成新的任务。

### 7.3 UGC 是后续的一条完整业务

只有用户主动表达想写、编辑句不能满足需要，且有人能处理审核和投诉时，再增加投稿。流程至少包括：用途说明 → 投稿 → 审核 → 可分发 → 撤回或举报 → 下架及缓存处理。

回音优先用可证明的口径，例如「昨夜，这句话送进了 12 份晚安」。如果只记录后端分发，就不能说 12 人读过；如果记录页面展示，也不能推断认真阅读。按稿件、接收用户和归属夜去重，明确历史回看不重复计数、本人不计数、失败与重试不计两次。

旧稿是否可以进入更大的公共池、是否可以被导出分享，要核对原用途和授权；不能默认一并开放。未审核、被撤回或被下架的内容不再对新用户展示。自己的回执遇到内容下架时显示替代说明，不悄悄换句后声称还是原句。已被他人导出的图片不能保证远程收回，应在投稿用途说明中讲清楚。

一次性留灯卡暂缓。只有观察到用户明确想对某个人说晚安，再围绕那个场景设计，不能仅因“可能有传播力”重建整套关系系统。

## 八、时间与数据口径：只定影响体验的规则

这一节是新实现必须遵守的产品约束，不代表当前代码已有这些能力。

### 8.1 首版支持范围

- 首版按 **北京时间 UTC+8** 定义夜晚，设置页明确展示。暂不承诺自动适配境外时区或轮班作息。
- 新模式目标范围为 **20:00–03:00，包含两端**；仪式窗口为目标前 3 小时至目标后 6 小时，包含起点、不包含终点。
- 因而最早开窗为 17:00，最晚结束为次日 09:00。服务端必须识别新模式并验证窗口，不能只靠前端把原有 12 小时窗口藏起来。
- 历史用户的时间、时区和记录不能静默裁剪到边界。进入新模式前展示其旧设置与新支持范围，让用户明确选择；在此之前保留兼容读取，不改写历史。

### 8.2 个人周期与公共夜晚分开命名

`cycleDate` 继续表达原有打卡的目标所在日期；新增 `nightId` 表达夜景所属的晚间日期。为完整覆盖支持的窗口，公共夜晚采用 **D 日 12:00 至 D+1 日 12:00**，标识为 D，固定北京时间。

| 目标与操作时间 | 原有目标日期 `cycleDate` | 晚间日期 `nightId` |
| --- | --- | --- |
| 目标 22:30，11 月 7 日 22:20 记录 | 20261107 | 20261107 |
| 目标 00:30，11 月 7 日 23:30 记录 | 20261108 | 20261107 |
| 目标 22:30，11 月 8 日 04:15 记录 | 20261107 | 20261107 |
| 目标 03:00，11 月 8 日 08:30 记录 | 20261108 | 20261107 |

新模式一名用户一晚最多一条有效仪式记录，以 `uid + nightId` 作为每日文档的权威身份；`cycleDate` 保留为目标日期元数据。旧版按 `uid + cycleDate` 的主键不能原样承担新规则：从 00:30 改成下一晚 22:30，两个不同夜晚可能具有同一个目标日期。

因此需要明确的记录版本和迁移边界：保留旧每日文档与历史统计，新规则启用后只写新模式每日文档，旧客户端对已迁移账号的写入也必须由服务端走同一规则，不能另写一份旧记录。新模式连续记录按 `nightId` 判断，累计在保留历史基础上每个新事实只增加一次。旧接口读取适配、跨版本重试和历史衔接必须在迁移设计中验证，不能承诺原接口无改动即可复用。记录保存当时的目标、规则版本及两种日期，不按之后的设置重算。

午夜目标的可记录窗口不一定覆盖整个公共夜，因此公共夜不能替代个人窗口授权。旧数据只在能够按原时间与规则可靠解释时用于个人回看，不能直接混入新模式公共人数。

### 8.3 晨间回执不等全局结算

个人回执在自己的记录确认后就已生成。页面状态依次判断：本次刚确认成功则保留完成态直到离开；再次进入且仍在个人窗口、尚未完成则展示关灯入口；已有该夜记录且已过 06:00 则展示回执。06:00 前已完成者仍看完成态。自己的下一夜窗口开启后回到下一夜的仪式，上一张回执仍可在历史里查看。

公共统计在 12:00 前只能称为「截至 HH:mm」，不能在某个用户 04:30 关窗时就宣布整夜结束。12:00 后完成聚合核对才标为已汇总；聚合延迟就继续显示更新时间，不为了晨报准点编最终数。以后若需要更早结算，必须重新定义支持窗口和数据规则。

北京时间日历日期为 D 时，「昨夜」固定指 `nightId = D-1`，不随当前窗口开启而变成今晚；「今晚」指 D 的晚间。午夜后仍开放的旧夜由个人窗口明确关联回 D-1，标题可写「这一晚」，不会借午夜重开一次。自己的窗口未开或已结束时，首页按第四节显示回执或待开窗状态，不直接套用公共夜边界。

「上次记录」单独查询并显示具体日期。长时间未使用后，不把最近有记录的旧夜替换成昨天；全局概览与个人旧回执也不能拼成仿佛同一晚。

### 8.4 改目标：保护正在进行的这一晚

v0.7 不沿用 v0.5 中可能因目标日期变化而跳过一晚的规则。新规则按 `nightId` 生效：

1. 当前夜已有记录，或旧目标窗口已经开始，修改都从下一夜生效；已结束的窗口也不重新打开。
2. 当前夜尚无记录，旧窗口和新窗口都未开始，可立即修改当前夜目标。
3. 旧窗口未开始但新窗口已经开始，修改从下一夜生效，不追溯打开一个已经开始的窗口。
4. 每次保存都按当前时刻与以上规则重算生效夜晚和开窗时刻，替换尚未生效的安排；不能只换目标、沿用旧的预约生效时间。已开始的夜晚、已有完成态和历史统计不动。设置页显示实际生效的夜晚及开窗日期时间。

例：11 月 7 日 22:00 把 22:30 改为 00:30，今晚仍按 22:30；新目标属于 11 月 8 日夜晚，其窗口从 11 月 8 日 21:30 开始。反向从 00:30 改为 22:30，同样从下一晚开始，不因 `cycleDate` 不同多跳一晚。

服务端保存生效边界并处理旧客户端写入；仅新增几个前端字段不够。对迁移用户可选择延后至下一完整夜启用新规则，确保旧窗口和新窗口不重叠。

公共人数不能在“请求返回成功之后”无条件 `inc`。可以在小规模阶段从事实记录生成去重快照；需要异步流水时，事件与事实记录在同一事务持久化，消费幂等、支持重放和对账。具体实现按容量验证选择。函数内存缓存仅属于实例，不能把它当作所有实例共享的一份可靠统计。

公开快照建议只返回 `nightId / count / updatedAt / finalized / statsVersion`；个人回执走身份校验，不能混入公共缓存。聚合不是“零隐私成本”：仍需说明采集用途、保留与删除规则，不外泄个人标识，不从公开结果反推个人行为。

好友功能从新版入口移除，不等于立刻删除云函数。仅返回「已下线」新错误码不会让现有旧客户端自动理解。保留旧路由与适当兼容响应，先掌握活跃版本和退出安排；不能拿“两个版本周期”当作可以删除的证据。旧数据的保留或删除按明确政策处理，本次不做删除。

旧心语的 `uid_date` 和奖励 ID 可能暴露作者标识；公开池启用前必须更换对外引用。删除投票按钮也不等于评分策略自动消失，需要同步检查候选池筛选。公共内容、数据用途与相册授权按实际后台要求和当前平台规则核对，不把通用模板当作提审结论。

## 十、路线图：先完成小闭环，再增加规模感

| 阶段 | 交付范围 | 本阶段要回答的问题 |
| --- | --- | --- |
| 体验样机 | 一套静态夜景、个人关灯动效、完成态、回执与分享落地演示 | 陌生人能否看懂动作，画面是否有辨识度，真机能否流畅运行？ |
| **P0：可使用的小闭环** | 真实关灯与恢复、稳定编辑句、个人昨夜回执、最近七晚、目标迁移、导出图、聊天转发与白天承接、最少埋点 | 无提醒会不会再来？是否自愿传播？接收者能否转成真实使用者？ |
| **P1：真实集体陪伴** | 去重公共统计、可见更新时间、可关闭的集体说明；验收后补朋友圈转发 | 少量真实同伴是否增加价值，值得持续承担数据成本吗？ |
| **P2：依据证据择一推进** | 有回看需求再做分布图；有表达需求再做 UGC 与回音；有审美需求再做主题与月相；有明确收件人需求再做留灯卡 | 哪一项能改善已观察到的问题，而非只是增加功能？ |

提醒不自动排成必做版本。先观察自然使用，再在用户主动提出需要时评估自愿订阅，区分收到提醒和未收到提醒的回访。不能用推送制造的打开掩盖产品价值，也不必永久禁止对用户有用的提醒。

P0 不含：全球排名、分钟级波浪、活跃比例窗、随机城市、天文日历、陌生人公共投稿、好友关系重建、群房间和任务系统。两种窗口口径、历史读取及分享承接属于基础正确性，不能以“先做视觉”为由延后。

不再估计“砍好友工程量减半”或“只加一个字段”。评估工作量至少分开：视觉样机、记录与迁移、回执、图片导出、分享落地、真机适配。排期从样机验证后开始，不因追求完美无限推迟，也不以编译通过代替可用。

## 十一、如何验证有机会成为爆款

### 第一步：先验证看懂与需要，不以好评过关

找约 10 名符合目标行为、没有读过方案的人。在真实微信环境分别从夜间首页和白天卡片进入，不先教操作。观察能否独立完成、是否知道记录了什么，以及会不会把背景窗当作真实在线用户。

工作门槛可暂定 8/10 独立完成，但它只用于暴露交互问题，不是市场需求证明。关键追问是「你会在什么具体时候想起它」「你原来怎么结束刷屏」「这张图你会发给谁、为什么」。少问抽象的“喜不喜欢”。

### 第二步：看没有提醒时会不会再来

招募 30–50 名目标用户，持续观察至少 14 天，让首批用户拥有完整的 7 夜及后续观察期。分开标记熟人、内容招募、外部分享带来的用户；记录招募话术。运营人员不每天私信催打卡，不用连续使用奖励污染自然回访。

| 问题 | 明确口径 | 如何用于决策 |
| --- | --- | --- |
| 首次是否顺利 | 已看到可用仪式入口的人中，首次服务端成功人数；另记失败、退出与耗时 | 技术失败和不愿使用分开，不把白天演示算激活 |
| 会不会重复使用 | 首次真实关灯所在夜起连续 7 个 `nightId`，完成至少 3 夜的人 / 有完整观察期的激活用户 | 暂以 30% 作为首轮投入判断线，沿用为工作假设；同时报告人数和来源 |
| 白天内容有无需求 | 昨夜有记录的人中，次日 06:00 至下一窗口开启前，实际看到个人回执的人数 | 单独测页面曝光，不用“次日任意打开”冒充；无需先规定 20% 为生死线 |
| 是否形成后续习惯 | 拥有完整 14 夜观察期的同批激活用户中，第 8–14 夜至少再使用一次的人数与比例 | 防止把前几天新鲜感当作稳定留存；缺席用户保留在分母，观察期未满的用户另列 |
| 传播能否带来新人 | 卡片生成 → 保存或分享发起 → 去重外部访问 → 首次真实关灯 | 不把前两步称为分享成功；归因缺失的访问单列 |

例如 30 人中 9 人达到三晚，只能作为继续小规模试验的信号。不能宣称统计显著、产品成功或已有行业竞争力。低于工作线，先按使用路径和访谈定位原因；可能是价值不足、用户不匹配、入口难找或技术问题，不直接归咎于完成页那一句话。

关灯确认到页面隐藏的时长只是“结束使用”的近似指标。系统切后台不代表入睡；退出接口成功也不证明停止刷其他应用。可在白天自愿访谈中补充体验，不在睡前加问卷。

### 第三步：验证传播闭环，不只验证素材

同期开三种真实内容入口，小量发布并分别记录来源：

1. **动作演示：** 冷白 → 暖黄 → 熄灭 →「今天先到这里」，约 6–8 秒；只展示当前版本确实有的体验。
2. **场景故事：** 「明明困了，却总想再看一会儿」对应的具体使用情境，检验是否招来需要它的人。
3. **个人回执：** 直接展示一张可实际得到的图，检验用户更在意文案、画面还是记录。

首轮优先同一两个能接触目标用户的渠道，使用有区分的公开来源标识。微信聊天卡作为直接体验路径；其他内容平台先验证内容是否吸引目标人群，再确认当前允许的引导方式和实际转化，不假设图片上的小程序码在各平台都可直接跳转。发布动作与渠道账号另行安排，本稿不代表已经发布。

传播测试至少要看到多位独立用户带来的接收访问和其中真实的新激活，而非只有创作者自己发出的流量。按完整观察期报告：**每 100 名激活用户，在随后 14 天带来多少名可归因的新激活用户**。同一新用户只计一次，发送者本人、测试号和原有用户剔除；没有完整观察期的队列暂不比较。

官方内容来源与个人分享来源分开；官方账号投放带来的新用户不算用户自传播。首轮归因规则固定为：新访客首次有效来源访问后 7 天内完成首次真实关灯，归给该来源；超过 7 天单列未归因，不反复覆盖来源。个人来源在服务端关联发送者，对外只用不透明标识。上述「随后 14 天」指标以接收者的激活发生时间为界，仅纳入发送者完整 14 天观察窗内的新增。

缺失与跨渠道转发会造成漏计，来源标识也不能证明因果；报告称为可归因结果，不当作全量传播真相。单次达到或未达到某个数值都不能证明长期自增长，必须结合第二批、第二周及获客成本。

### 继续、收缩或转向

| 观察结果 | 下一步 |
| --- | --- |
| 画面被记住，复用弱 | 回到使用场景和实际收尾价值，不继续堆月相或换皮 |
| 夜间复用好，白天回看弱 | 保持夜间产品，回执轻量保留，不把晨报强行升级为主线 |
| 回看和收藏好，接收激活弱 | 检查分享表达、落地页与白天演示，不急着奖励邀请 |
| 有多来源的重复使用，也有独立用户带来新激活 | 继续投入一小轮，优先验证公共陪伴或被主动要求的能力 |
| 两轮针对性改进后仍只剩“好看”、无人自然复用 | 停止扩建日用产品，评估做成可分享的轻体验或换场景 |

商业化暂不放进关灯主链路。只有稳定复用后再验证可选主题等付费意愿，基本仪式、已有记录和退出不设付费门槛。也不把匿名投稿内容或个人作息做成广告画像。没有成本与付费数据前，不写盈利预期。

## 十二、进入开发和上线的验收边界

这是后续开发的清单，本次只交付方案。

- **产品理解：** 新用户不被误导为睡眠监测；演示与真实记录清楚区分；背景窗不被标成陌生人状态。
- **记录与时间：** 服务端窗口校验、一晚一次、重复点击、超时已提交、改目标、旧新版并用；覆盖 22:30、00:30、03:00、跨午夜、开窗与关窗的精确边界。
- **回执：** 同一晚重进不换句；跨日、不活跃后回归、无记录、内容版本更新都正确；个人数据不进入公共缓存。
- **界面：** 按仓库要求完成 `yarn verify`，并实际打开微信模拟器检查页面及窄屏；真机分别验证长按、轻点、退后台、退出、字体、减少动效和图片导出。
- **分享：** 真机检查聊天卡、公开页、白天演示、小程序码；朋友圈单页能力通过后再开启；相册拒绝不影响其他功能。
- **迁移：** 新目标规则和旧版本兼容先落地；旧好友路由与链接保留可用去向；无未经确认的旧数据删除和旧稿用途扩大。
- **容量与运营：** 按测得的调用量估算每千次关灯及分享的读写、函数和存储成本，压测夜间峰值；UGC 上线前具备实际处理举报和下架的人与流程。
- **发布核对：** 产品名称可用性、账号主体与类目、AppID、环境、隐私指引及素材版权按真实情况核实。构建、模拟器、真机、云端联调、部署分别报告。

本次查阅的微信开发文档主站部分页面未能直接读取；平台细节由微信官方 GitHub 类型与 CloudBase 官方资料交叉核对。它们用于纠正方案中的不准确假设，不代表本项目已经通过平台审核或真机测试。

## 十三、本版建议确定的决策

1. **核心承诺：** 给今天一个结束动作；真实陪伴辅助成立，不靠规模才成立。
2. **首版闭环：** 关灯、个人回执、最近七晚、分享及接收落地一起验证。
3. **晨报定位：** 降为个人回看，不把每天早上回来设为使用义务。
4. **明确删除：** 精确序号、在线或清醒推断、等待连锁熄灯、首版复杂天文视觉。
5. **下一项交付：** 一套可在真机体验的关灯与回执样机，随后做有完整观察期的小范围试用。

**这一版是否值得继续投入，取决于用户是否在下一晚主动回来、是否自愿把它带给别人。**
