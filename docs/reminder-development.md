## 产品决定

- 「我的」增加「关灯提醒」，进入独立页面；今晚首页、真实完成态和演示中不增加提醒弹窗。
- 用户选择北京时间 20:00—次日 05:59 中的一个时间，默认 22:30。页面显示这一次的明确月日和时间，才由用户点「订阅这一次提醒」。默认值是本轮设计选择，可在页面修改，不是个人关灯目标。
- 提醒日期取最近可用的夜晚：已过或不足一分钟的时间、本人已关灯的夜晚、已尝试发送提醒的夜晚，移到下一夜。到提交时过期则拒绝并要求重新确认，不在后台悄悄改到明天。
- 一次主动订阅只对应一次预约；最多一条待发预约。改变预约需先取消，再重新订阅。没有永久开关、累计授权余额或每日自动续订。
- 拒绝、取消和订阅接口失败不会创建预约；不能从 `getSetting` 的历史选择推导出新的订阅授权。
- 发送前检查该夜真实记录，已经关灯则跳过。超过预约时间五分钟或超过 06:00 不再发起发送；微信自身的到达延迟无法由小程序控制。
- 待发时可以取消；已领取发送则明确提示无法撤回。发送结果不明、平台拒绝、进程中断均不自动重发，优先避免重复打扰。微信已发出的消息无法撤回。
- 返回小程序仍进入 `pages/night/index`。消息不带个人句子、精确关灯时间或个人来源参数。

## 接口与存储

仍由 `bedtimeNight` 从微信上下文鉴权，新增三个动作。所有请求继续拒绝额外业务字段，接受平台保留的传输字段但不从中取身份。响应沿用 `{ code, data }`；成功包含 `serverNow, userId, enabled, templateId, reminder, lastAttemptNightId, testUntil`。正常使用的 testUntil 为 null；客户端兼容旧响应缺少该字段。

| 动作 | 参数 | 说明 |
| --- | --- | --- |
| getReminder | 无 | 只读本人最新预约；没有预约为 null |
| scheduleReminder | requestId、revision、nightId、time、templateId | 使用已展示的夜晚与时间，服务器重新检查配置、时间、原记录与版本 |
| cancelReminder | requestId、revision | 只取消匹配的本人待发预约；重复取消幂等 |

`getState` 增加 `reminderAvailable`；客户端仅在服务端配置可用且身份已确认时显示入口。没有模板或开关关闭时仍可查询、取消已有预约，不能创建新预约。提醒配置错误不阻断核心关灯。

预约放在 `n_users/{OPENID}.reminder`，每个用户只保留最近一次，字段为 requestId、revision、nightId、time、dueAt、status、templateId、createdAt、可选 attemptedAt / finishedAt。`reminderLastAttemptNightId` 在同一用户档案中单独保存，防止用新 requestId 在同夜再次发送。它不属于每日关灯统计。

客户端投影只包含 requestId、revision、nightId、time、dueAt、status。无新集合、客户端直读直写或提醒事件表；原三集合个人删除仍会完整清除提醒。只读统计脚本不使用这些字段。

预约状态：pending → sending → sent / failed / unknown；pending 也可变为 cancelled / skipped / expired。sending 超过五分钟对客户端投影为 unknown，但永远不重新入待发队列。

同一 requestId 重试只返回原预约（包括已取消或已发送状态），不能复活预约或改变时间。不同 requestId 必须匹配上一版本；旧取消或旧重试不能覆盖后来安排。保存超时先回读，也可以沿用原 requestId 重试，不再次请求订阅。客户端晚到回调检查页面可见性与身份代际。

## 定时发送与成本

新云函数 `bedtimeReminderDispatch` 与关灯写入分离。只接受没有小程序 OPENID 的可信定时调用：通用云定时器的 `TRIGGER_SRC=timer`，或微信定时器的 `TCB_SOURCE=wx_trigger` 且存在平台 `WX_TRIGGER_API_TOKEN_V0`。这些字段只从平台环境读取；不能凭客户端伪造的 event / tcbContext 获得批量发送权限。每分钟触发一次：`0 * * * * * *`，名称 `nightReminderMinute`。

索引为 n_users 的 `reminder.status ASC + reminder.dueAt ASC`。每次最多读十条到期预约，并发处理；事务内重新读本人档案和当夜记录，先将预约改为 sending 并记录本夜已尝试，再在事务外调用微信。事务领取回执不明不发消息；外部发送六秒未确认则 unknown。回写必须仍匹配 requestId、revision、sending；不能覆盖新预约或重建已删除的档案。

该策略不是 exactly-once 投递承诺：领取后、请求微信前崩溃可能漏发；请求微信后丢回执可能实际已送达。微信接口没有此处可用的幂等回执查询，因此不把未知状态重新投递。时间检查到真正发送间存在短暂竞争，用户在消息已开始处理时完成关灯或取消，仍可能收到它。

维护成本是每天 1,440 次定时调用及其查询，活跃预约另有事务与发送请求。初版最多处理十条/分钟；大量同时到期或长时间停机会导致过期跳过，不承诺高流量准点送达。日志只输出各结果数量或固定错误码，不记录 OPENID、预约全文、夜句和消息收件人。
