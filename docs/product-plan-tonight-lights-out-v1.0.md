## 零、这份文档怎么用

v1.0 是**施工稿**，不是讨论稿。它假设方向已经定了，目标是让一个小团队照着它开工，尽量少回来问问题。

两个前提把方案简化了一半：

**没有老用户。** 所以 v0.7 和 v0.8 里那一整章 `cycleDate` 与 `nightId` 共存、legacy 标记、旧客户端双写、旧记录只读兼容——**全部作废**。数据模型可以一次设计对，现有 `checkins` / `goodnight` / `friends` 三套集合直接弃用，代码整体重写而非改造。这省下的不只是工期，更是长期的认知负担。

## 一、一页体验

这一页里没有一个「不」字。它是给美术、视频和对外沟通用的。

晚上十一点多，你还在刷手机。你知道该睡了，但总想再看一会儿。

你退出当前这个 App，从微信下拉，点开「今晚关灯」。

屏幕上是一栋楼的夜景，几十扇窗模糊地亮着。中间偏左有一扇窗比别的清楚，泛着很淡的冷白光，像有人还醒着。那是你的窗。

下面一行小字：灯还亮着。

你把拇指按在那扇窗上。窗由冷白转成暖黄，像有人把吸顶灯换成了床头灯。暖光慢慢向窗芯收拢，八百毫秒。

松手的瞬间，一声极轻的「嗒」，手腕上一下微震。窗灭了。

然后整块屏幕暗下去，全黑。你手里只剩一块黑色的玻璃，房间也跟着暗了一度。

两秒半，黑着。

一句话很淡地浮出来：

> 今天就到这里。剩下的，明天再说。

你读完它。此刻把手机扣下，这一晚就结束了。如果你还拿着，再过三秒，屏幕最下面会出现一行很暗的字：放下手机。旁边还有一行更小的：今晚的灯迹。

点开灯迹，是一条横在黑底上的细线，上面有几十盏小灯，高低起伏，那是今晚所有人关灯的时刻。你那一盏是暖色的。

第二天中午以前你再打开它，它会给你昨夜：那扇窗、那句话、你关灯的时间，和最近七晚。你可以把那句话存成一张图。

## 二、产品定义

### 2.1 一句话

> **给舍不得结束今天的人，一个轻轻关灯的动作。**

产品名「今晚关灯」是动作，对外口号「今天先到这里」是情绪。两句用在不同场合，同一屏里只出现一句。

### 2.2 给谁

夜里已经觉得该休息、却习惯继续刷微信或短视频的人。他们试过屏幕使用时间、Forest、早睡打卡，最后都因为"又多了一个任务"而放弃。年龄大致 20–35 岁，但行为比年龄重要。

他们要的是一个很低成本的结束动作：

> 我已经决定今晚先到这里，帮我用几秒钟把这个决定落下来。

### 2.3 承诺

按住关灯，几秒钟完成，没有后续任务。今晚这一句只属于今晚，第二天还能看到自己读过的那句。你留下的一笔是真实的，别人的记录也是真实的，而且都不暴露身份。随时可以离开。

### 2.4 为什么是微信小程序

这个产品的核心动作是"结束使用手机"，而用户必须先打开微信才能用上它。这个尴尬无法回避，但可以变成设计前提：**承认用户已经在微信里了。**

于是「添加到我的小程序」不是一个顺带提一句的弱提示，而是这个产品**唯一的免费入口资产**——微信下拉即达，不用搜索，不用记名字，不用占桌面图标。它在第四节有专门的设计位置，在第十二节有专门的观测口径。

## 三、四个核心设计

整个产品就是这四件事。其余都是它们的容器。

### 3.1 三拍完成：屏幕真的暗下去

这是产品唯一能被身体记住的反馈，也是 8 秒视频的高潮。用户睡前面对的是屏幕，只有屏幕本身暗下去，"关灯"才从比喻变成事实。

关键在于**节奏，而不是动画**。完成态分三拍：

| 拍 | 时间 | 画面 | 设计意图 |
| --- | --- | --- | --- |
| 第一拍 | 0 – 2.5s | 纯黑。一个字都没有。关灯声和震动发生在 0s | 让"结束"单独发生。这 2.5 秒的空白是整个产品最贵的资产 |
| 第二拍 | 2.5 – 5.5s | 今晚的句子淡入，宋体，极低对比度 | 句子是奖励，不是结束的一部分 |
| 第三拍 | 5.5s 起，且用户仍在页面 | 底部浮现「放下手机」和「今晚的灯迹 ›」 | 产品等你，而不是抓你 |

**第三拍的时机设计是有意的。** 如果用户在第一拍就把手机扣下了，他永远看不到任何按钮——这是最好的结局，产品的目的达到了。如果他还拿着，说明他愿意多待一会儿，这时才给他东西看。陪伴感只在用户主动停留时出现，它从不催促停留。

这同时解决了前几版的一个老问题：v0.6 在睡前编造陪伴，v0.7 删掉陪伴，v0.8 把陪伴推迟到第二天——而睡前的孤独才是真问题。第三拍让陪伴在正确的时刻、以正确的强度出现。

**实现只用全屏黑色遮罩，坚决不碰系统亮度。** `wx.setScreenBrightness` 改完不会自动恢复，而 `onUnload` 在切 Tab 和退后台时不触发（今晚页就是 Tab 页，`onUnload` 实际上几乎永远不执行），微信开放社区有真实案例是用户退出后手机停在最低亮度。它在 OLED 上相比遮罩几乎没有增益，却带来一类无法自愈的故障。把它彻底移出路线图，省得反复讨论。

遮罩规格：`position: fixed` 全屏，`background: #000`，`opacity` 从 0 到 1，1.2 秒，`ease-out`。遮罩之上才是句子层。LCD 屏上背光不变，效果弱于 OLED，这是已知差异，第 1 周必须两种屏都看一眼再定遮罩的最终不透明度和句子的对比度。

**三拍必须用绝对时间戳驱动，不能用 `setTimeout` 排队。** 这是最容易写错、而且错了很难发现的地方：用户在第一拍就把手机扣下是**理想结局**，而这会触发 `onHide`，小程序进入后台后定时器被冻结——如果用 `setTimeout` 链，用户几小时后回来会看到句子"刚刚"才淡入，整个节奏荒谬。

正确做法是把 `confirmedAt`（服务端时间）存进页面状态，三拍的边界是 `confirmedAt + 2500` 和 `confirmedAt + 5500`，渲染时永远按 `Date.now()` 比较当前落在哪一拍：

| 情形 | 行为 |
| --- | --- |
| 正常停留 | `requestAnimationFrame` 或 200ms 轮询推进拍数，动画正常播 |
| `onHide` 后 60 秒内 `onShow` | 按当前时间直接跳到对应拍，**不补播动画** |
| `onHide` 超过 60 秒后 `onShow` | 直接给第三拍的静态版，无动画、无声音、无震动 |
| 窗口仍未关闭时重新进入页面 | 同上，静态第三拍 |

### 3.2 关灯声：黑暗里唯一的反馈

屏幕黑了以后，视觉通道就关闭了。**此刻声音是唯一还能工作的反馈通道**，而几乎没有同类产品在用它。

一声极短、极轻的「嗒」，像拉绳开关或者墙上的翘板开关。不是提示音，不是音效，是一个物件的声音。它在服务端确认成功的那一刻播放，和震动同时发生。

这同时是品牌资产：8 秒视频里，画面变黑之后只剩这一声，比任何 logo 都好记。

| 项 | 规格 |
| --- | --- |
| 时长 | 120–200ms，单声道，无混响尾巴 |
| 音量 | 峰值压到 -18dBFS 左右，宁可轻到有人听不见 |
| 格式 | mp3，8KB 以内，随包体打进 `assets/audio/click.mp3` |
| 播放 | `wx.createInnerAudioContext()`，页面 `onLoad` 预创建并预加载 |
| 开关 | 「我的」里可关，持久化到本地与服务端 |
| 震动 | `wx.vibrateShort({ type: 'light' })`（基础库 2.13.0+），独立开关，默认开 |

**静音键这件事要按平台分别处理，不能想当然。** `obeyMuteSwitch` 的默认值确实是 `true`，但有两个坑：实例上的这个属性自基础库 2.3.0 起已经不生效，必须用全局的 `wx.setInnerAudioOption({ obeyMuteSwitch: true })`；更重要的是**它只在 iOS 生效**——Android 没有独立的静音开关语义，夜里把手机调静音的安卓用户照样会被这一声吵到。

所以「用户调静音 = 明确表示别出声」这个产品前提在安卓上不成立。结论：

| 平台 | 关灯声默认 |
| --- | --- |
| iOS | 开，跟随静音键 |
| Android | **关**，用户在「我的」里主动打开 |

安卓用户首次成功关灯后，第三拍里额外给一行一次性的小字「想听见关灯声？在『我的』里打开」，点击直达设置，关掉后不再出现。

`wx.vibrateShort` 的 `type` 参数同样只在 iOS 生效，Android 固定 15ms；iOS 用户若在系统里关掉了触感反馈会走 `fail`，**静默吞掉，不提示、不降级**。

### 3.3 今晚一句：每晚都不同的内容单元

每个 `nightId` 对应一句编辑写好的晚安句，当晚所有用户看到同一句。完成页、回执、夜签图、公开页用的都是这一句。同一晚重进不换句，第二天回看仍是当时那句。

它解决两件事：第三晚之后有新东西可看；一句话是内容型传播的最小单位。

**「同一晚同一句」的真正理由在产品外面。** 用户在产品里看不见别人，也无从知道别人读的是同一句，所以它在应用内制造不了什么"共同经验"。它不可替代的价值是**传播时的同句共振**：当某一晚小红书上有三十个人发了同一句话，那是可被认出来、可形成话题的。这个理由要求夜签图的排版必须让句子足够显眼、足够像一张"能被认出来的卡"，而不是一张应用截图。第十节会落实这一点。

代价是容错性：某晚那句话不合某个人的心境时，他当晚没有备选。先接受这个代价，如果上线后这类反馈集中出现，再加一个每晚限一次的「换一句」，但不要动排期机制本身。

**内容规格。** 1–2 行，40 字以内。语气短、平、暖，允许一点点幽默。写的是"结束今天"，不是睡眠建议，不是鸡汤，不是运势。首发 30 句，按 `nightId` 排期，相邻两晚不重复，同一句至少隔 30 晚再回来。

### 3.4 灯迹：真实的陪伴，n=1 也成立

一条横在黑底上的细线，上面是按 10 分钟聚合的关灯次数，横轴 17:00 到次日 09:00。没有坐标轴，没有网格，没有排名，只有高低起伏的小灯。用户自己的时刻是暖色的那一盏。

它一次解决三个问题：冷启动时不寒酸（一盏灯的线也好看）；完全诚实（每一盏都是真实的关灯记录，按用户与夜晚去重）；可传播（它是一张有形状的夜景，而不是一个数字海报）。

**冷启动的关键设计：数字比形状更容易显得凄凉。** 「今晚的灯迹」配一条只有三盏灯的线，看起来是克制；「今晚有 3 次关灯」看起来是没人用。所以：

| 当夜计数 | 显示 |
| --- | --- |
| < 20 | 只画形状，标题「今晚的灯迹」，不出现任何数字 |
| ≥ 20 | 形状 + 一行小字「今晚 N 次关灯，你是其中之一」 |

这个阈值写在服务端配置里，可以随时调，客户端只读服务端给的 `showCount` 布尔值。

**隐私补丁。** 单个 10 分钟桶内计数低于 3 时，与相邻桶合并渲染，不单独体现高度差。否则在用户量小的时候，结合分享出去的"你在 23:18 关的灯"，理论上可做交叉推断。

**数据来源。** `n_nights` 集合是事实，`n_stats/{nightId}` 是每 10 分钟由定时任务重算的缓存，关灯写入路径上绝不更新全局文档。完成页展示的是**当前快照**，最差延迟 10 分钟，完全可接受；自己刚写入还没进快照时，本地把自己那一盏高亮上去，但不改动计数。

### 4.1 今晚页的状态机

服务端返回 `phase` 和一组绝对时间戳，**客户端只做比较，绝不自己推算窗口**。

| 条件 | 形态 |
| --- | --- |
| 本夜有记录，`now < windowCloseAt` | 完成态（第三拍已展开的静态版） |
| 本夜有记录，`now >= windowCloseAt` | 本夜回执 |
| 本夜无记录，`phase = open` | 关灯仪式 |
| 本夜无记录，`phase = before` | 等待开窗。有昨夜记录时，下方接昨夜回执 |
| 本夜无记录，`phase = closed` | 已结束态 |
| 很久没来，本夜无记录 | 等待开窗 / 已结束态，下方用具体日期显示「上次留下的夜晚」 |

**有一个容易漏的长空窗。** 目标 03:00 的用户，窗口在 09:00 关闭，而 `nightId` 要到 12:00 才翻页——于是 09:00–12:00 是 `closed`，12:00 一到跳回 `before`，但下一次开窗要等到当天 00:00，中间有十几个小时都停在「等待开窗」。这是正确行为，但文案必须说清楚是哪一天：开窗时刻落在次日凌晨时，写「明天 00:00 开窗」而不是「今晚 00:00 开窗」。判断规则是比较 `windowOpenAt` 与当前北京日历日，跨日就用「明天」。


首次进入时，你的窗旁边有一个很小的标签「你的窗」，出现 4 秒后淡出，之后永不再现（本地标记）。状态只靠颜色区分是不够的，必须有这个一次性文字锚点。

按压过程中，「灯还亮着。」淡出，画面只剩收拢的光。按满后文案变成「正在确认」。

超过目标时间仍可关灯，文案换成「晚一点，也可以把今天放下。」按钮文字不变。

### 4.2.1 长按与轻点的完整参数

这一节是 `hold-button` 组件的规格，开发直接照做。

| 参数 | 值 |
| --- | --- |
| 判定阈值 | 800ms。从 `touchstart` 起算，到达即触发提交 |
| 色温过渡 | `touchstart` 起 600ms 冷白 → 暖黄，与收拢并行 |
| 光收拢 | 800ms，与判定阈值同步，光环半径线性收到窗芯 |
| 滑出容差 | 手指移出控件外接矩形 **24px** 以上判定取消 |
| 滚动锁 | 控件上 `catchtouchmove`，按压期间页面不滚动 |
| 取消回弹 | 300ms，`ease-out`，光回到起始状态，文案恢复 |
| 提交后 | 立即进入「正在确认」，控件禁用，**取消监听所有手势** |
| 确认超时 | 8 秒。超时显示「暂时没确认，点此查看结果」，点击走一次 `getState` 而不是重新提交 |
| 重复触发 | 组件内置 `submitting` 标志；但这只是体验保护，**幂等由服务端 `_id` 保证** |

**「轻点也可以」的含义必须一次定清楚：它是跳过长按、直接提交的等价入口，不是一个提示。** 理由是无障碍——手部不便、戴手套、或者单纯不理解长按的用户必须有一条完整的路。

实现上它是主按钮下方一行独立的可点文字，触控区不低于 44px 高。点击后跳过 600/800ms 的按压动画，直接播 400ms 的收拢然后提交，后续三拍完全一致。两条路径调用同一个 `submit()`，服务端看不出区别，埋点里用 `method: 'hold' | 'tap'` 区分。

## 五、视觉规范

### 5.1 构图：一栋楼，不是一座城

v0.6 的 240 扇窗城市网格是通用的，而且把复杂度推给了 Canvas。v1.0 改成更亲密、也更容易做好的构图：**一栋楼的局部立面**占据画面中上部，你的窗在中间偏左，是唯一清晰的窗；其余窗柔焦，纯粹是背景，不承载任何状态。

这让整个夜景可以是**一张静态分层 PNG**，彻底绕开 Canvas 逐帧动画、240 个动画节点、设备性能判定这一整类问题。

分层：

| 层 | 内容 | 实现 |
| --- | --- | --- |
| 0 | 天空渐变 | WXSS `linear-gradient`，不出图 |
| 1 | 远处楼体剪影 + 柔焦窗 | 一张 PNG，≤ 180KB |
| 2 | 近处楼体与窗框 | 一张 PNG，≤ 120KB |
| 3 | 你的窗 | WXSS 绘制的一个矩形 + 光晕精灵图 |
| 4 | 遮罩 | 纯色 `view`，`opacity` 过渡 |
| 5 | 文字 | 普通 DOM |

Canvas **只用在两处**：夜签图的一次性导出，和灯迹的静态绘制。两者都是画一次就不动，没有帧率问题。

### 5.2 色板

| 用途 | 色值 | 说明 |
| --- | --- | --- |
| 夜空（顶） | `#140F1E` | 深紫，不是纯黑也不是蓝黑 |
| 夜空（近地平线） | `#2E2230` | 城市光污染的褐紫辉光 |
| 楼体剪影 | `#0C0A12` | 几乎黑，只靠轮廓存在 |
| 柔焦背景窗 | `#3A3340` | 低对比，刻意看不清 |
| 你的窗 · 冷白 | `#CFE2F0` | LED 灯，略偏青 |
| 你的窗 · 暖黄 | `#F0B055` | 钨丝灯，仪式进行中 |
| 你的窗 · 熄灭 | `#171320` | 玻璃反光，比楼体亮一点点 |
| 正文 | `#E8E2D6` | 暖白，不用纯白 |
| 弱化文字 | `#9A8F9C` | 实色，不靠透明度 |
| 完成页文字 | `#6B6459` | 黑底上的极低对比，刻意不刺眼 |

**暖黄是唯一的强调色**，只出现在三个地方：你的窗、主按钮描边、灯迹上你自己那一盏。任何其他位置都不许出现暖黄。

### 5.3 字体与字阶

标题、句子、数字用宋体：`"Songti SC", "STSong", "Noto Serif CJK SC", serif`。正文、按钮、状态用系统无衬线。

Android 上宋体常常缺失，**降级路径必须在第一周就在真机上确认**。句子是动态内容无法做字体子集，所以结论大概率是接受系统衬线降级，那就要保证无衬线版本的排版同样成立——这意味着句子的字号、行高和留白要在两种字体下各看一遍。

| 元素 | 字号 / 行高 |
| --- | --- |
| 完成页句子 | 19px / 2.0，宋体，字间距 0.05em |
| 回执句子 | 17px / 1.9 |
| 320px 窄屏句子 | 16px 起，宁可多一行 |
| 状态文字 | 13px |
| 按钮 | 16px |
| 灯迹说明 | 12px |

### 5.4 动效

全产品只有五处，其余一律没有。

| # | 动效 | 规格 |
| --- | --- | --- |
| 1 | 你的窗呼吸 | 4s 一周期，`opacity` 0.82 ↔ 1.0 |
| 2 | 进入页面夜景渐显 | 1.5s，`ease-out`，每次进入只一次 |
| 3 | 按压：冷白转暖黄 | 600ms 色相过渡，紧接暖光向窗芯收拢 800ms |
| 4 | 熄灭 | 光收成一点，1.0s |
| 5 | 遮罩暗屏 | 1.2s，`ease-out`，紧接三拍节奏 |

不做卡片入场、悬停、滚动淡入，不做"其他人跟着你熄灯"的连锁动画。

「减少动效」开启后：1、2 关闭；3 缩短为 200ms 直切；4、5 保留但缩短到 400ms——**暗屏不是装饰，是动作本身，任何情况下都不取消**。

### 5.5 可达性

主按钮和所有文字按钮的触控区不低于 44px 高。覆盖 320px 宽、系统放大字号。深底对比度实测，弱化文字用实色而非透明度。状态绝不只靠颜色传达：你的窗有一次性文字标签，完成态有文字。

## 七、时间模型

这是整个后端最需要一次写对的部分。干净重建，没有历史包袱。

### 7.1 支持范围

全部按**北京时间 UTC+8**，设置页明示。首版不适配境外时区和轮班作息。

目标范围 **20:00–03:00，含两端**，步进 10 分钟。仪式窗口是 **目标前 3 小时至目标后 6 小时**，含起点、不含终点。

因此最早开窗 17:00，最晚结束次日 09:00。范围限制不是偷懒——它保证**所有窗口都完整落在一个 `nightId` 内**，这让整个数据模型少掉一整类边界问题。服务端必须独立校验窗口，前端的判断只用于渲染。

### 7.2 nightId

公共夜晚定义为 **D 日 12:00 至 D+1 日 12:00**，标识为 D。

```text
nightId       = dateKey( beijingNow - 12h )
targetAt      = D 日 12:00 之后第一次出现 targetHM 的时刻
windowOpenAt  = targetAt - 3h
windowCloseAt = targetAt + 6h
phase         = now < windowOpenAt  ? 'before'
              : now < windowCloseAt ? 'open'
              :                       'closed'
```

验算：

| 目标 | 操作时刻（北京时间） | `nightId` | 说明 |
| --- | --- | --- | --- |
| 22:30 | 11-07 22:20 | 20261107 | 22:20 − 12h = 10:20 (11-07) |
| 22:30 | 11-08 04:15 | 20261107 | 04:15 − 12h = 16:15 (11-07) |
| 00:30 | 11-07 23:30 | 20261107 | 23:30 − 12h = 11:30 (11-07)；目标落在 11-08 00:30 |
| 03:00 | 11-08 08:30 | 20261107 | 08:30 − 12h = 20:30 (11-07) |
| 20:00 | 11-07 17:30 | 20261107 | 17:30 − 12h = 05:30 (11-07) |
| 任意 | 11-08 12:00:00 | 20261108 | 12:00 整属于新的一夜 |

`dateKey` 返回 `YYYYMMDD` 字符串。所有时间计算先把 `Date.now()` 加上 8 小时偏移，再按 UTC 取日期——**绝不使用服务器本地时区**，云函数的时区是不可控的。

### 7.3 改目标

一名用户一夜最多一条记录。改目标按 `nightId` 生效：

1. 当前夜已有记录，或旧目标窗口已经开始 → 从下一夜生效。已结束的窗口也不重新打开。
2. 当前夜无记录，且旧窗口和新窗口都还没开始 → 立即对当前夜生效。
3. 旧窗口未开始、新窗口已经开始 → 从下一夜生效，不追溯打开一个已经开始的窗口。
4. 每次保存都按当前时刻重算生效夜和开窗时刻，替换尚未生效的安排。已开始的夜晚和已有记录不动。设置页必须显示实际生效的夜晚和开窗时间。

用户记录存 `targetHM / targetAt / windowOpenAt / windowCloseAt / ruleVersion`，**记录保存写入当时的规则，不按之后的设置重算**。

## 八、数据模型

**八个集合，全部新建。** 现有环境里已经存在 `users` 集合（而且 `cloudfunctions/database-indexes.json` 里给它建了 `uid_unique` 唯一索引），所以新集合一律加 `n_` 前缀，和旧集合在同一环境里并存互不干扰；旧集合在新版上线、确认无流量之后统一 drop，写进第十四节的清理脚本。

### `n_users/{uid}`

```text
{
  uid,                      // openid
  targetHM: '22:30',
  pendingTargetHM: null,    // 待生效目标
  targetEffectiveNight: null, // 'YYYYMMDD'，pending 从哪一夜开始
  prefs: {
    sound: true,            // Android 端建档时写 false，见第六节
    haptics: true,
    dimScreen: true,
    reduceMotion: false
  },
  firstRef: null,           // 首次带参访问的来源
  firstRefAt: null,
  createdAt,
  updatedAt
}
```

### `n_nights/{uid}_{nightId}`

文档 ID 直接拼 `uid` 和 `nightId`，**唯一性由 docId 保证，不依赖事务内查询**。CloudBase 的事务只适合按文档 ID 读写。

```text
{
  _id: `${uid}_${nightId}`,
  uid, nightId,
  targetHM, targetAt, windowOpenAt, windowCloseAt,
  status: 'hit' | 'late',   // confirmedAt <= targetAt ? hit : late
  confirmedAt,              // 服务端时间，权威；三拍的时间基准
  bucket,                   // 10 分钟桶，'HHmm'，用于聚合
  phraseId, phraseText, phraseVersion,
  ruleVersion: 1,
  createdAt
}
```

### `n_phrases/{nightId}`

```text
{
  nightId, phraseId, text, version,
  status: 'published' | 'withdrawn',
  publishedAt
}
```

排期可以提前写满 30 天。缺失时服务端按 `nightId` 哈希从内置池选一句并即时补写——**补写必须和 `n_nights` 用同样的幂等写法**，否则 23:00 的并发会同时去创建同一个 `_id`（见第 9.1 节的重复键处理）。

### `n_stats/{nightId}`

```text
{
  nightId,
  count,                    // 去重后的关灯人数
  buckets: [{ t: '2310', n: 7 }, ...],   // 10 分钟一格
  showCount: false,         // count >= 阈值时为 true
  updatedAt, finalized,
  statsVersion: 1
}
```

### `n_cards/{cardId}`

```text
{
  cardId,                   // = sha256(uid + nightId + SALT) 前 16 位
  nightId, phraseText, dateLabel,
  createdAt, expiresAt      // 30 天
}
```

`cardId` 用确定性哈希而非随机数，这样同一个用户对同一夜反复点「发给朋友」只会产生一个文档。随机 ID 会让集合无限膨胀，也会让「夜签生成数」这个指标虚高。哈希里有盐，所以从 `cardId` 反推不出 `uid`。

### `n_refs/{ref}`

```text
{
  ref,                      // 随机不透明码
  channel,                  // 'xhs' | 'video' | 'chat' | 'image' | ...
  campaign,
  createdAt
}
```

### `n_config/{key}`

运行时可调的参数，避免为了改一个阈值去发版。

```text
{ key: 'trailShowCountThreshold', value: 20 }
{ key: 'boardOpenIds',            value: ['oXXX...', 'oYYY...'] }
{ key: 'statsFullRecalcLimit',    value: 3000 }
```

### `n_events/{autoId}`

埋点落库。**不能用 `wx.reportAnalytics` 替代**——第 12.3 节要的"带参进入按渠道分""提示展示/点击转化"这类口径，微信自定义分析导不出来，所以这里没有"二选一"，必须自建。

```text
{ uid, name, props, nightId, ts }
```

客户端做批量上报：事件先进内存队列，满 10 条或页面 `onHide` 时一次性提交，失败丢弃不重试（埋点丢几条无所谓，别为它加复杂度）。

### 索引

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `n_nights` | `uid` ASC + `nightId` DESC | 归档分页、最近七夜、上次记录 |
| `n_nights` | `nightId` ASC + `bucket` ASC | 统计聚合 |
| `n_cards` | `expiresAt` ASC | 清理 |
| `n_events` | `ts` DESC | 看板 |

### 数据库规则

`n_users`、`n_nights`、`n_events`、`n_config` 仅云函数可读写。`n_phrases`、`n_stats`、`n_cards` 可设为所有人可读、仅管理端可写，以便必要时走 CDN。客户端**绝不直连数据库**，一律经云函数。

## 九、云函数接口

两个函数。`common/` 继续作为共享模块。

### `bedtimeNight`

统一入口 `{ action, payload }`，统一返回 `{ ok, code, data, message }`。身份一律从 `cloud.getWXContext().OPENID` 取，客户端传的 uid 一概忽略。

| action | 入参 | 返回 |
| --- | --- | --- |
| `getState` | — | `serverNow, nightId, phase, targetHM, targetAt, windowOpenAt, windowCloseAt, record|null, lastRecord|null, recentSeven[], stats, prefs, pendingTarget` |
| `closeLight` | `{ clientNightId, method }` | `record`（含 `phraseText`、`confirmedAt`）、`stats`、`isFirstEver` |
| `setTarget` | `{ targetHM }` | `targetHM, pendingTargetHM, targetEffectiveNight, effectiveOpenAt` |
| `setPrefs` | `{ prefs }` | `prefs` |
| `getArchive` | `{ cursor, limit }` | `items[], nextCursor` |
| `createCard` | `{ nightId }` | `cardId` |
| `readCard` | `{ cardId }` | `nightId, phraseText, dateLabel, count?, showCount` |
| `track` | `{ events[] }` | `ok` |
| `getBoard` | `{ days }` | 看板数据，openid 需在 `n_config/boardOpenIds` 里 |

`recentSeven` 的结构固定为七项，从今夜往前推七个 `nightId`，无记录的夜也要占位：

```text
[{ nightId: '20261107', has: true,  status: 'hit',  hm: '23:18' },
 { nightId: '20261106', has: false, status: null,   hm: null   }, ...]
```

`getArchive` 的 `cursor` 是**上一页最后一条的 `nightId`**，查询条件为 `uid == me && nightId < cursor`，按 `nightId` 降序取 `limit` 条。首次不传 `cursor`。`items` 里每条带 `nightId, dateLabel, phraseText, hm, status`；**归档详情页要显示那一夜的灯迹形状，所以 `items` 还要带 `buckets`**——但别在列表接口里返回，改成点开详情时单独调一次 `readCard`-风格的轻接口按 `nightId` 取 `n_stats`。

### 9.1 重复键的正确写法

**`closeLight` 的流程**，顺序很重要：

1. 取 `n_users` 文档，若无则建档（默认 22:30；安卓端 `prefs.sound = false`）。
2. 按服务端时间算 `nightId / targetAt / windowOpenAt / windowCloseAt / phase`。
3. `phase !== 'open'` → 返回 `code: 'WINDOW_CLOSED'` 和下次开窗时间。
4. `clientNightId` 与服务端不一致 → 返回 `code: 'NIGHT_CHANGED'`，让客户端刷新后重来。
5. 取 `n_phrases/{nightId}`；缺失则按哈希生成并用下面同一套写法补写。
6. 用 `_id = ${uid}_${nightId}` 执行 `add`。
7. 读 `n_stats/{nightId}` 一并返回（允许为空）。

第 6 步的错误处理不能靠判断错误码。云开发把 MongoDB 的 E11000 包成 `errCode: -502001 / FailedOperation.DuplicateWrite`，而 `-502001` 同样用于权限失败等其它场景，**没法可靠分支**。正确写法是：

```js
try {
  await coll.add({ data: { _id, ...payload } })
  return payload
} catch (e) {
  // 不解析错误码：任何写入失败都先去读一次
  const got = await coll.doc(_id).get().catch(() => null)
  if (got && got.data) return got.data   // 已存在 → 幂等成功
  throw e                                 // 真失败 → 抛出
}
```

这同时覆盖了客户端超时但服务端已写入的场景：用户重试时拿回的是同一条记录和同一句话。`n_phrases` 的补写用完全一样的模式。

### 9.2 读放大

`getState` 在 23:00 前后是读峰值。逐项数一遍：1 条 `n_users`、1 条 `n_nights`（本夜）、1 条 `n_phrases`、1 条 `n_stats`、最近七夜 7 条、以及**「上次记录」1 条**——长期未使用的用户那条记录不在最近七夜里，需要单独一次 `limit(1)` 查询。合计 **12 次**。

优化：最近七夜在客户端缓存，仅跨夜失效，命中时服务端跳过这一段，降到 5 次。「上次记录」只在 `recentSeven` 全为空时才查。

验收这件事不能靠"实测调用次数"——小程序侧拿不到逐次的数据库读计数。改成在云函数里自己维护一个计数器，`getState` 返回前把本次读次数打进日志，在云控制台看日志验证。

### 9.3 `bedtimeStats`

定时触发，每 10 分钟一次。**只在 17:00–09:00 这个有意义的时段跑**，其余时间直接返回，省掉一半调用。

重算当前 `nightId` 和前一个 `nightId` 两份 `n_stats`。前一夜在 12:00 之后标 `finalized: true`，之后不再重算。

**用聚合，不要用 `get()` 循环。** 云函数端 `collection.where().get()` 单次最多返回 100 条，手写分页既慢又容易漏：

```js
const res = await db.collection('n_nights').aggregate()
  .match({ nightId })
  .group({ _id: '$bucket', n: $.sum(1) })
  .end()
```

一次请求拿到全部 96 个桶（17:00–09:00 共 16 小时 × 6）。`count` 另用 `.count()` 取。

什么时候该改成增量：**单夜记录数超过 3000**。前面写的 5 万是我估高了一个数量级——1 万条记录每 10 分钟全量扫一次，一天就是几百万次读，基础版额度撑不住。在代码里把这个阈值读 `n_config/statsFullRecalcLimit`，超过就切到"只统计上次 `updatedAt` 之后的新增并累加"。

触发器**不随 `yarn upload:cloudfunctions` 走**。它配在云函数目录下的 `config.json` 里，开发者工具需要"上传并部署"和"上传触发器"两步；现有的 `cloudfunctions/deploy.js` 里没有任何 trigger 处理。要么补脚本，要么在第十四节的清单里写死这是一个手动步骤——**别假设部署一次就生效，上线后第一晚一定要回云控制台确认触发器真的在跑。**

## 十、分享、夜签图与公开页

### 10.1 夜签图

这是用户唯一会主动传播的东西，必须做成**一张句子卡，而不是一张应用截图**。

| 项 | 规格 |
| --- | --- |
| 尺寸 | 1080 × 1440（3:4） |
| 构图 | 上 55% 是夜景（楼与你的那扇暗窗 + 一颗星），下 45% 是纯夜色底 |
| 主元素 | 句子，宋体，居中，占画面宽度的 70%，**是全图最大的视觉元素** |
| 次元素 | 日期「二〇二六年十一月七日 夜」，小号，句子下方留白两行之后 |
| 角标 | 右下角「今晚关灯」四字 + 小程序码，合计不超过画面宽度的 18% |
| 不印 | 精确关灯时间、昵称、头像、账号信息、人数 |

**夜签图要出两版模板。** `getUnlimited` 生成的小程序码要求小程序**已经发布**才能用，所以第 0 周做素材前测时根本拿不到码——那一版模板右下角只放「今晚关灯」四个字。产品上线后换成带码的版本，内容账号和用户生成的用同一版，这样第十一节说的"账号发的和用户发的是同一张图"才成立。`scene` 参数上限 32 字符，够放一个 `ref`。

**为什么不印时间和人数：** 这张图要像一句话，不像一份数据报告。用户自己的回执页里能看到时间，那是私密视图。

**实现上有一个必须绕开的坑：`canvasToTempFilePath` 不支持 `wx.createOffscreenCanvas` 创建的离屏画布**，照着"离屏绘制后导出"去写，在 iOS 上会拿到全白图或直接报错。而上屏的 `<canvas>` 如果用 `display: none` 隐藏，导出同样是空白。

正确做法：

```text
<canvas type="2d" id="signCanvas"
        style="position:fixed; left:-9999px; top:0; width:270px; height:360px" />
```

用 `position: fixed` 移出视口而不是隐藏；`createSelectorQuery().fields({ node: true, size: true })` 拿到 node，按 `dpr` 放大画布的实际像素；`wx.canvasToTempFilePath({ canvas, destWidth: 1080, destHeight: 1440 }, this)` ——**在自定义组件里调用时第二个参数必须传 `this`**，否则选择器找不到节点。

绘制前必须等所有图片资源 `onload` 完成（用 `canvas.createImage()`，注意它是异步的），否则会导出一张只有文字没有夜景的图。1440px 的高度远低于部分 Android 约 4096px 的导出上限，这里安全。

**相册权限被拒后不能在 `fail` 回调里直接调 `wx.openSetting`**——自基础库 2.3.0 起它必须由用户点击触发。流程是：`saveImageToPhotosAlbum` 失败 → 弹一个 `showModal`（「需要相册权限才能保存。也可以长按图片保存。」）→ 用户点「去设置」才调 `wx.openSetting`。同时始终保留"长按图片保存"这条兜底路径。不反复弹授权。

### 10.2 聊天卡片

`onShareAppMessage` 固定返回：标题是当晚那句话（而非产品口号），图片是 5:4 的窗景，路径指向 `pages/open/index?card=<cardId>&ref=<ref>`。

朋友圈 `onShareTimeline` 用 1:1 封面，在单页模式能力真机验收通过之后才开放。

### 10.3 公开页

`pages/open/index?card=<cardId>&ref=<ref>`，无需任何授权即可读。

```text
          [ 夜景 ]

      今天就到这里。
      剩下的，明天再说。

      二〇二六年十一月七日 夜

   ─────────────────────────

   有人在今晚关了灯。
   按住一扇窗，给今天画个句号。

      [   试试关灯   ]
```

「试试关灯」按时间跳转：夜间且窗口已开 → 真实仪式；其余 → 演示。**今晚页是 Tab 页，`wx.switchTab` 不支持 query**，所以"进入即演示"这个意图要用 `globalData` 或 storage 写一个一次性标记，今晚页在 `onShow` 里消费掉它。这是个很容易在联调时才发现的坑，提前写清楚。

`cardId` 失效时展示产品介绍和今晚开窗时间，绝不出现空白错误页。

公开接口只返回 `nightId / phraseText / dateLabel / count? / showCount`。不返回 uid、不返回发送者的任何信息、不返回精确时间。

### 10.4 归因

新 `ref` 是随机码，`refs/{ref}` 存 `channel` 和 `campaign`，对外只出现 `ref`。新访客首次带 `ref` 进入时服务端记 `firstRef / firstRefAt`，7 天内完成首次真实关灯才归因，之后不覆盖。

**图片里的小程序码是通用码，只能归到「图片」这个渠道，无法归到某个具体发送者。** 这是首版的诚实限制，接受它，别为了归因去给每个用户生成带参码。

## 十一、增长：内容账号才是引擎

这是 v1.0 相对前几版最大的策略调整。

前几版都把增长寄托在"用户生成夜签图并分享"上。但一个新产品没有用户，也就没有人分享，这是个死循环。而这个产品恰好有一个特殊属性：**它每天都有一句话。**

所以：**真正的增长引擎是一个每天发一句话的内容账号，小程序是它的落地页。**

| 项 | 做法 |
| --- | --- |
| 阵地 | 小红书为主，视频号为辅 |
| 节奏 | 每晚 22:00–00:30 发一张当晚的夜签图，和产品内是同一句 |
| 成本 | 接近零。图是产品自己生成的，句子是已经排好期的 |
| 内容 | 纯句子卡。不介绍功能，不写"快来用"，评论区放小程序 |
| 视频号 | 每周一条 8 秒视频，内容见下 |

这件事有三个独立的好处：它让"同一晚同一句"的设计第一次真正发挥作用（账号发的和用户发的是同一张图，互相放大）；它在产品还没做完的时候就能开始，**是唯一一个不需要用户就能跑起来的验证**；它积累的是品牌资产，即使产品失败，账号本身也还有价值。

### 8 秒视频

| 时间 | 画面 |
| --- | --- |
| 0 – 1.5s | 暗房间，只有手机屏幕亮着，屏幕里是夜景和一扇窗 |
| 1.5 – 3.0s | 拇指按住那扇窗，窗由冷白转暖黄 |
| 3.0 – 4.2s | 窗熄灭，整块屏幕暗下去，房间随之变暗。一声「嗒」 |
| 4.2 – 4.8s | 全黑。什么都没有 |
| 4.8 – 6.5s | 一句话浮出：今天就到这里。剩下的，明天再说。 |
| 6.5 – 7.2s | 手机被扣在床边，屏幕的光消失 |
| 7.2 – 8.0s | 一行字：今晚关灯 |

不配音，不解释，不加「快来试试」。看点是第 3 秒到第 5 秒：**手机真的暗了，然后黑了一会儿**。必须真机实拍。

## 十二、没有调研，怎么知道做对了

这是本方案最需要换思路的一节。既然拿不到 10 个人做可用性测试，也拿不到 30 人做留存观察，就得换三种办法。

### 12.1 先测素材，再测产品

**这是最便宜、最该先做的一件事，而且现在就能做。**

在写第一行代码之前，用设计稿导出 **10 张夜签图**（10 句不同的话），发到小红书。不挂链接，不提产品，就看内容本身的互动。

两个必须说清楚的限制：

**不要做概念版 8 秒视频。** 第十一节说了视频必须真机实拍，而这时候产品还不存在，拍不出来。第 0 周只测静态图，视频等 M1 跑通之后再拍。

**判据只能是相对排序，不能是绝对通过线。** 一个新账号第一周发十条笔记，互动接近零是默认结果——这既可能是句子不行，也可能只是账号没有权重，两者分不开。所以要看的是**十句之间的相对差异**：哪两三句的收藏和转发明显高于其余，为什么。那几句的语气就是产品该走的方向。

相应地，这一步的决策权要降级：它**不能否掉整个方向**，它决定的是句子的风格和夜签图的排版。如果十句里一句都没有任何水花，那就再换十句试一轮，而不是放弃产品。

这件事花一周，可能省掉两个月的文案返工。

### 12.2 自己当第一个用户，连续用 14 晚

M1 一上线，自己先连续用两周，每晚记三件事：今晚是什么时候想起它的、关灯之后有没有立刻去刷别的、第二天有没有主动打开过。

这不是严谨方法，但它能暴露最致命的问题——**如果连作者自己第五晚就忘了用，这个产品不成立**，不需要再找用户来证明。很多产品死于作者从来没真正用过自己的东西。

### 12.3 让产品自己告诉你

做一个极简的**看板页**，`pages/board/index`，云函数侧用 openid 白名单控制访问。每天早上看一眼：

| 指标 | 口径 |
| --- | --- |
| 昨夜关灯人数 | `n_stats/{nightId}.count` |
| 新用户数 | 昨夜 `n_users.createdAt` 落在该夜的数量 |
| 首次关灯人数 | 昨夜有记录且是本人第一条记录 |
| 回头率 | 昨夜有记录的人里，7 天内还有过其它记录的比例 |
| 3/7 | 最近 7 个 `nightId` 内有 ≥3 夜记录的人数与占比 |
| 白天回看 | 昨夜有记录的人里，窗口关闭后打开过的人数 |
| 夜签生成 | 昨日 `cards` 新增数 |
| 带参进入 | 昨日带 `ref` 的新访客数，按渠道分 |
| 下拉添加提示 | 首次提示展示数 / 点击数 |

埋点事件清单（客户端上报到一个轻量集合或直接用微信自定义分析，二选一，不要两套）：

| 事件 | 属性 |
| --- | --- |
| `night_open` | `phase`，`hasRecord` |
| `hold_start` / `hold_cancel` / `hold_complete` | — |
| `close_result` | `ok`，`code` |
| `beat3_shown` | 用户停留到第三拍 |
| `exit_tap` / `exit_result` | `ok` |
| `trail_open` | — |
| `receipt_view` | — |
| `card_create` / `card_save` / `card_share` | — |
| `open_page_view` | `ref`，`channel` |
| `addto_prompt_show` / `addto_prompt_tap` | — |

**事件里绝不带句子全文、精确个人时间或任何第三方可识别信息。**

### 12.4 什么时候该收手

没有大样本，就别假装做统计推断。用一组粗糙但诚实的判断线，**至少积累 100 个激活用户、运行 4 周**之后再看：

| 观察 | 结论 |
| --- | --- |
| 3/7 ≥ 25%，且有非作者来源的新激活 | 成立。继续投入一轮，优先做灯迹和内容账号 |
| 3/7 ≥ 25%，但传播几乎为零 | 产品成立、分发不成立。重做夜签图和内容账号，别买量 |
| 3/7 < 15%，但夜签图互动高 | 它是一个内容项目，不是一个日用工具。转向账号，产品当落地页 |
| 3/7 < 15%，夜签图也无人问津 | 两轮针对性改进后仍如此，停止扩建 |

**第三行是真实可能的结局，而且不算失败。** 一个每天有十万人看一句话的账号，比一个每天有一百人打卡的小程序更有价值。方案要允许这个结果发生。

## 十四、上线清单

**品牌与资质。** 小程序名称、图标、导航标题、分享标题统一为「今晚关灯」；准备 2–3 个备选名以防重名。类目按「工具」或「生活服务」申请，**避开医疗健康类目**——描述写「一个帮助你在夜间结束使用的仪式工具」，绝不出现睡眠监测、改善睡眠、助眠等字样，否则会触发资质要求。

**隐私。** 更新《小程序用户隐私保护指引》，覆盖 openid、关灯记录与时间、目标时间、分享来源、分析事件、**相册写入**。`saveImageToPhotosAlbum` 是隐私接口，未在指引中声明会被直接拦截——这是最容易在提审前一天才发现的坑，第 4 周就要提交。

**内容与版权。** 30 句全部原创或已获授权，不引用歌词、诗句、网络热评。夜景插画、图标、字体、音效逐项核对授权。音效如果用素材库，确认商用许可。

**云端。** 新建八个集合、四条索引、数据库规则；`n_config` 预写阈值和看板白名单。`bedtimeStats` 的触发器配在函数目录的 `config.json` 里，**现有的 `cloudfunctions/deploy.js` 不处理触发器**——要么补脚本，要么在开发者工具里手动走"上传并部署"和"上传触发器"两步，并在上线首夜回控制台确认它在跑。测试环境先完整跑通一整夜再动生产。旧集合（`users` / `checkins` / `goodnight` / 好友相关）在新版上线并确认无流量后统一 drop，连同 `database-indexes.json` 里的旧索引一起清理。

**真机。** `yarn verify`；模拟器查 320px、长句、放大字号；iOS 与 Android 各测长按、轻点、退后台、暗屏、退出、夜签导出、相册拒绝、聊天卡片、公开页、减少动效、宋体降级。`wx.exitMiniProgram` 需要基础库 2.17.3+、必须用户点击触发、开发者工具里不生效，**只能真机验收**；低版本基础库用 `<navigator open-type="exit">` 兜底，PC 端微信的行为不做保证。

**成本。** 按预估量估一次每千次关灯的函数调用、数据库读写和存储。这个产品的流量形状极端集中在 22:00–00:30，压测要按这个形状做，不要按平均值。

## 十五、红线

所有"不做"集中在这里。前面十四节只讲做什么。

**诚实。** 绝不伪造关灯人数。绝不推断用户是否清醒、是否入睡、是否还在玩手机。绝不把关灯时间说成入睡时间。绝不显示"你是第 N 个"这类无法精确保证的序号。绝不把本产品的记录称为全国样本或睡眠数据。背景窗是美术，绝不标注成其他用户的状态。

**克制。** 不做连续天数、断签清零、补签、排行榜、等级、徽章。不做每日推送。不以分享换取任何功能或奖励。不在完成页弹窗、倒计时或要求分享后才能退出。不把"放下手机"做成需要先完成别的事才能点的按钮。

**边界。** 首版不做好友关系、双人窗、群房间、UGC 投稿、留灯卡、月相与天文视觉、地域或群组切片、商业化。这些都等到第十二节的判断线给出明确信号之后再谈。

**技术。** 不碰系统亮度。不用 Canvas 做逐帧动画。不在关灯写入路径上更新任何全局计数文档。不在 `getState` 里查询历史全量。不依赖 `benchmarkLevel` 判断设备。不让客户端直连数据库。不把客户端传的 uid、日期、状态当作可信输入。

**隐私。** 公开页面和卡片上不出现 uid、昵称、头像、精确关灯时间。埋点不带句子全文和精确时间。灯迹的单桶计数低于 3 时与相邻桶合并。

## 十六、决策记录

记下来是为了以后不要反复讨论同一件事。

| 决策 | 为什么 | 否决了什么 |
| --- | --- | --- |
| 完成态用三拍，第三拍延迟出现 | 空白是这个产品最贵的资产；陪伴只在用户主动停留时出现 | v0.6 的等待连锁熄灯、v0.8 把灯迹全部推到第二天 |
| 只用遮罩，不碰系统亮度 | 改了不会自动恢复，`onUnload` 在切 Tab 和退后台不触发，故障无法自愈，而 OLED 上增益接近零 | v0.8 的"M0 验证、M1 可能开启" |
| 加关灯声 | 屏幕黑了之后声音是唯一还在工作的反馈通道，也是最便宜的品牌资产 | — |
| 同一晚同一句 | 价值在产品外的同句共振，不在产品内的共同经验 | v0.8 对这一点的错误论证；也否决了按用户哈希分配 |
| 灯迹在计数 < 20 时只画形状 | 数字比形状更容易显得凄凉 | v0.6 的三段阈值切换画面 |
| 一栋楼，不是一座城 | 静态分层图就能做好，绕开 Canvas 性能、设备判定、240 节点这一整类问题 | v0.6 的 240 扇窗网格 |
| 目标限制 20:00–03:00 | 保证所有窗口完整落在一个 `nightId` 内，消掉一整类边界问题 | 支持任意目标时间 |
| 删掉全部旧集合与旧页面 | 没有老用户，兼容是纯成本 | v0.7 / v0.8 的整章迁移设计 |
| 增长引擎是内容账号 | 新产品没有用户就没有分享，这是死循环；而产品每天自带一句话 | "靠用户生成夜签图传播"这一单点假设 |
| 先测素材，再写代码 | 唯一一个不需要用户就能跑的验证，能在一周内否掉整个方向 | 先做产品再找人看 |
| 允许"它其实是个内容项目"的结局 | 一个每天十万人看一句话的账号，比一个一百人打卡的小程序更有价值 | 必须做成日用工具的执念 |
